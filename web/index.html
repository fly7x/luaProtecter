How it works

One script in, three stages, one protected file out

FŁY is organized the way its source tree is organized: a transform stage, an obfuscation stage, and an emitter that writes the result. Nothing about the order is hidden from you — include/protector/config.hpp is where you turn stages on, off, or up.

stage 1 · src/transformer.cpp

Transform

Your script is parsed and rebuilt as an equivalent program with a different shape: control flow is restructured and the lexical layout you wrote is discarded, while the logic it expresses is kept intact.

stage 2 · src/obfuscation.cpp

Obfuscate

Identifiers, string literals, and constants are replaced and encoded. What's left no longer carries the names and text that made the original easy to read at a glance.

↓
stage 3 · src/emitter.cpp

Emit

The transformed program is written out as a single file — output/protected.lua — ready to ship in place of the source it replaced.

optional · third_party/luau

Luau integration

Add Roblox's Luau as a git submodule and FŁY's CMake build will link against it automatically — the USE_LUAU option is on by default, and off cleanly if the submodule isn't present.

Techniques

What the obfuscation stage actually does

Each technique targets a different way scripts get reverse-engineered — reading the names, reading the strings, or just reading the control flow top to bottom.

renaming

Identifier stripping

Locals, upvalues, and function names are replaced with short, meaningless symbols, so nothing in the output hints at what a variable was for.

encryption

String encoding

Literal strings — including anything that looks like a key, URL, or message — are encoded at build time and decoded at runtime, never sitting in the file as plain text.

control flow

Flow rebuilding

Branches and loops are re-expressed so the file's structure no longer mirrors your original source, which blunts tools that work by pattern-matching familiar shapes.

constants

Constant masking

Numeric literals are rewritten as small expressions that evaluate to the same value, so a reader can't just scan for the number they're after.

single-file output

Flattened emission

The emitter writes one self-contained file. There's no separate manifest or side-table describing what was renamed to what.

build-time

Zero runtime dependency

Protection happens once, at build time, in a native CMake project. The script you ship needs nothing extra installed to run.

Why it's worth the build step

Readable source is an open door

A plain .lua file tells a reader almost everything: variable names describe intent, strings reveal endpoints and secrets, and the control flow is laid out exactly as written. Each FŁY stage removes one of those signals.

Get started

Building FŁY takes one submodule and CMake

No package manager, no installer — clone it, optionally wire in Luau, and build.

git submodule add https://github.com/Roblox/luau.git third_party/luau
mkdir build && cd build
cmake -DUSE_LUAU=ON ..
cmake --build .
# protected file is written to output/protected.lua

FAQ

Before you build

Do I need Luau installed to use FŁY?

No. Luau integration is optional and controlled by the USE_LUAU CMake flag, which defaults to on. If third_party/luau isn't present, CMake skips the integration and FŁY builds without it.

Does protected output run differently from the original script?

No — every stage is built to preserve behavior. What changes is how the file reads, not what it does when it runs.

Can I run FŁY as part of a build pipeline?

Yes. It's a native CMake project with a Dockerfile included, so it drops into a CI step the same way any other native build tool would.

Is obfuscation reversible?

No obfuscator makes a script impossible to read with enough effort — FŁY's job is to raise the cost of that effort well past what copying a public script would normally take.
