Documentation

Everything you need to build FŁY, wire in Luau, and run your first script through the protector. FŁY is a native C++ / CMake project — there's no package manager step, just a clone and a build.

Overview

FŁY protects Lua and Luau source files by rewriting them through a three-stage native pipeline before they ship. You give it input/script.lua; it gives you back output/protected.lua — a file that runs the same way but no longer reads the way the original did.

The project builds with CMake and optionally links against Roblox's own Luau compiler and runtime, added as a git submodule. That integration is controlled by a single CMake option, USE_LUAU, which is on by default.

FŁY is distributed as source. Building it yourself means you always know exactly what binary is processing your scripts.

Installation

Clone the repository, then decide whether you want Luau integration before your first build — it's easiest to add the submodule up front.

1. Clone the repository

git clone https://github.com/fly7x/luaProtecter.git
cd luaProtecter

2. Add Luau as a submodule (recommended)

FŁY's CMake looks for a Luau checkout at third_party/luau. Adding it as a submodule is the supported way to provide one:

git submodule add https://github.com/Roblox/luau.git third_party/luau
git submodule update --init --recursive

If you skip this step, CMake detects the missing directory and builds FŁY without Luau integration instead of failing — see build options.

3. Configure and build

mkdir build && cd build
cmake -DUSE_LUAU=ON ..
cmake --build .

On a clean checkout this produces the FŁY binary inside build/. Point it at a script under input/ to produce a protected file under output/ — see Running the protector.

If CMake reports that it can't find a Luau target, the submodule's own CMakeLists may export it under a different target name than FŁY expects. See Troubleshooting.

Build options

FŁY currently exposes its Luau integration as a single CMake switch.

OptionTypeDefaultEffect
USE_LUAUboolONWhen on, CMake looks for a Luau CMakeLists.txt under third_party/luau and adds it as a subdirectory, then links the luau target against FŁY if one exists. When off, FŁY builds without attempting Luau integration at all.
 
# build without Luau integration
cmake -DUSE_LUAU=OFF ..
cmake --build .

This is the right choice if you only need the transform / obfuscate / emit pipeline and don't need Luau's compiler or runtime linked in.

Docker build

A Dockerfile ships at the repository root, so you can build FŁY in a container instead of installing a toolchain locally — the same approach a CI pipeline would use.

docker build -t fly-obfuscator .
docker run --rm -v "$PWD/input:/app/input" -v "$PWD/output:/app/output" fly-obfuscator

Mount your own input/ and output/ directories as shown so files make it in and out of the container.

Project layout

The repository is organized around the three pipeline stages, with a clear split between source, generated third-party code, and the script files you're protecting:

luaProtecter/
├── src/
│   ├── main.cpp            entry point, wires the pipeline together
│   ├── transformer.cpp/.hpp    stage 1 — control-flow rebuilding
│   ├── obfuscation.cpp/.hpp    stage 2 — renaming, string & constant encoding
│   └── emitter.cpp/.hpp        stage 3 — writes the protected file
├── include/
│   └── protector/
│       └── config.hpp      pipeline configuration
├── input/
│   └── script.lua          put the script you want protected here
├── output/
│   └── protected.lua       FŁY writes the result here
├── third_party/
│   └── luau/                ← official Luau source goes here (submodule)
├── web/                    this site's source
├── CMakeLists.txt
└── Dockerfile

Running the protector

Place the file you want to protect at input/script.lua, then run the binary you built:

./build/fly-obfuscator

A protected copy is written to output/protected.lua. Run the binary with --help to see the flags available in your checkout — they're a faster source of truth than any document for exactly which options your build was compiled with.

Keep your original source under version control somewhere outside output/. Protected files aren't meant to be edited by hand.

Config reference

include/protector/config.hpp is where the pipeline's behavior is defined at compile time. The table below describes the kind of switches you'll find there by category — check the header in your own checkout for the exact names and defaults shipped in your version.

CategoryStageControls
flowtransformerWhether control-flow rebuilding runs, and how aggressively branches and loops are restructured.
namingobfuscationThe identifier scheme used when renaming locals, upvalues, and functions.
stringsobfuscationWhether string literals are encoded, and which encoding is used.
constantsobfuscationWhether numeric literals are rewritten as equivalent expressions.
luaubuildMirrors the USE_LUAU CMake option for code that checks it at compile time.

Pipeline stages, in detail

Transformer

Parses the input script and rebuilds its control flow into an equivalent form. This runs first because every later stage works against the rebuilt structure, not your original layout.

Obfuscation

Walks the rebuilt program and replaces the things a reader relies on: identifier names become opaque symbols, string literals are encoded, and numeric constants are rewritten as expressions that evaluate to the same value.

Emitter

Serializes the fully processed program back out as valid Lua, written to output/protected.lua. This is the only stage that touches the filesystem for output.

Troubleshooting

CMake can't find a Luau target

FŁY's CMake tries to link a target literally named luau if the Luau submodule's own CMake defines one. If the version of Luau you added exports a different target name, update the target_link_libraries call in the top-level CMakeLists.txt to match it.

Luau submodule not detected

Confirm third_party/luau isn't empty — a submodule that was added but never initialized leaves the directory present but bare. Run git submodule update --init --recursive and reconfigure.

Build works without Luau

This is expected behavior, not an error: when third_party/luau has no CMakeLists.txt, FŁY skips the integration and builds the core pipeline on its own.

FAQ

Is a Lua interpreter required to build FŁY?

No — FŁY is a C++ project built with CMake. Luau is only needed if you want its compiler or runtime linked in for compile-time checks against Luau-specific syntax.

Where do I report a bug?

Open an issue on the GitHub issue tracker with your CMake configuration, OS, and whether USE_LUAU was on.
